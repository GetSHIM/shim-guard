`scripts/probe/probe.py`; the captures are committed, sanitised, under

## T1 — does `PostToolUse` carry the full text of a `Read` result?

**Yes.** The hook receives exactly the bytes the model receives, verbatim.

`Read` on a 65,798-byte, 824-line file produced a `PostToolUse` payload of
56,294 bytes whose `tool_response.file.content` held 54,837 bytes over 686
lines. The content is a verbatim substring of the source file. The client had
truncated the read itself and said so in the payload:

```json
"tool_response": {
  "type": "text",
  "file": {
    "filePath": "/probe/workspace/big.txt",
    "content": "Contact alice@example.com for access.\n00001 The quick brown fox …",
    "numLines": 686,
    "startLine": 1,
    "totalLines": 824,
    "truncatedByTokenCap": true
  }
}
```

The model then read the remainder with `offset: 687, limit: 200`, and that
second `PostToolUse` carried the remaining 10,960 bytes — again verbatim, again
complete relative to what the model saw.

This is the answer PRD-05 needed. Inbound masking of file contents **is**
possible on Claude Code, and it is complete: there is no case where the model
sees text the hook did not. Where the client truncates, it truncates before the
hook, and it labels the truncation.

## Surprises

Four findings that contradict, or are absent from, the vendor documentation.
Each has a test.

### 1. `PostToolBatch` serialises a `Read` result differently from `PostToolUse`

The same `Read`, in the same turn, appears twice in two different shapes.

`PostToolUse.tool_response` is a structured object with the raw file body:

```json
{"type": "text", "file": {"content": "services:\n  api:\n …", "numLines": 7}}
```

`PostToolBatch.tool_calls[].tool_response` is a **string**, with line numbers
prepended, exactly as the model is shown it:

```json
"1\tservices:\n2\t  api:\n3\t    image: example/api:1\n…"
```

This matters for PRD-05 R4. "The value must match the tool's output shape" is
not one shape per tool — it is one shape per tool *per event*. An adapter that
learns the `PostToolUse` shape and reuses it at `PostToolBatch` will emit an
object where a string is expected. Pinned by
`test_read_results_use_two_different_shapes_across_events`.

`PostToolBatch` also fires for a single tool call, not only for batches of two
or more. It is a superset of `PostToolUse`, not a companion to it, so listening
to both means scanning the same bytes twice.

### 2. `WebFetch` results never reach the hook as HTML

The vendor documentation describes `WebFetch` as fetching and converting a
page. What arrives at `PostToolUse` is not the page:

```json
"tool_response": {
  "bytes": 559,
  "code": 200,
  "codeText": "OK",
  "url": "https://example.com",
  "result": "# Example\n\nThe page describes a domain designated for documentation purposes…",
  "durationMs": 1838
}
```

`bytes` is the size of the response the client fetched; `result` is a
model-generated summary of it. The HTML is consumed inside the client and is
never exposed to any hook.

**Consequence for PRD-07.** R1 lists "HTML to Markdown for `WebFetch` results"
as a transform. On the Claude Code hook path there is no HTML to convert, and
the summary is already shorter than anything a transform could produce. That
transform only becomes real under `shim watch` (PRD-09), where the wire body is
visible. PRD-07 should either drop it or move it, and should not claim a byte
reduction it cannot deliver here. Pinned by
`test_web_fetch_results_never_reach_the_hook_as_html`.

### 3. `SessionEnd` fires, but its output is never rendered

Extending the probe to emit `{"systemMessage": "…"}` from every event and
reading the client's own `--include-hook-events` stream back:

| Event | Hook ran | `systemMessage` shown to the user |
|---|---|---|
| `UserPromptSubmit` | yes | yes |
| `PreToolUse` | yes | yes |
| `PostToolUse` | yes | yes |
| `PostToolBatch` | yes | yes |
| `Stop` | yes | yes |
| `SessionEnd` | yes | **no** |

The `SessionEnd` payload is delivered to the hook — the capture exists — but the
client emits neither a `hook_response` record nor an `informational` line for
it. The process is shutting down and nothing further is rendered.

**This answers PRD-06 Q6.2.** The session summary must be emitted at `Stop`, not
at `SessionEnd`. `Stop` also carries `last_assistant_message` and
`stop_hook_active`, the latter being the guard against a summary that re-triggers
itself.

### 4. `PostToolUseFailure` carries no result field at all

A failed `Bash` call delivers `error` as a plain string and omits
`tool_response` entirely:

```json
"error": "Exit code 1\ncat: no-such-file.txt: No such file or directory",
"is_interrupt": false
```

An adapter that reads `tool_response` unconditionally will `KeyError` on every
failed tool. `error` is inbound text like any other and should be scanned:
a failing command frequently echoes the credential it failed with.

## Payload sizes and the existing analysis limits

One `Read` produced 54,837 characters of scannable text in a single event.
`normalize.MAX_SOURCE_CHARACTERS` is 100,000 and raises rather than truncating,
and `hook.py` converts any exception into a hard block. A single large file
read is therefore already within a factor of two of the limit that would, today,
block the user's session. PRD-05 R5's size cap and its `observe` fallback are
not a nicety; they are what stops tool events from turning the detector's
bounds into an outage.

## Method, exactly

```bash
python scripts/probe/probe.py run "$CLAUDE_BINARY" --root /tmp/probe --model sonnet
python scripts/probe/probe.py fixtures --root /tmp/probe \
    --destination tests/fixtures/probe/claude
python scripts/probe/probe.py summary --fixtures tests/fixtures/probe/claude
```

`scripts/probe/capture_hook.py` writes raw stdin to `$SHIM_PROBE_DIR` and
returns empty stdout and exit 0, so a probe session behaves exactly like a
session with no hook installed. `scripts/probe/mcp_echo_server.py` is a
one-tool stdio MCP server, so the MCP captures are real protocol traffic rather
than a hand-written guess.

Fixtures are named `<event>-<tool>-<step>-<n>.json`. PRD-01 R3 specified
`<event>-<tool>.json`; the step qualifier was added because the T1 comparison
needs the large-file and small-file `Read` captures side by side under the same
event and tool, and one file name cannot hold both.

Sanitisation replaces the probe root, the home directory and the interpreter
path — each in both literal and slug form, because Claude Code embeds the
working directory into `transcript_path` with every separator turned into a
hyphen — and rewrites UUIDs and `toolu_`/`msg_` identifiers to stable ordinals.
Every value in the workspace is synthetic: `alice@example.com`, AWS's own
published example key `AKIAIOSFODNN7EXAMPLE`, and invented tokens.
`test_fixtures_carry_no_machine_identity` fails if any of that regresses.
